# 把想法聊成设计

## 触发条件
**任何创造性工作开始前**：新功能、新组件、加功能、改行为。
不是改 typo、不是跑测试、不是看代码——只要你准备写新代码或改行为，先走这个 skill。

## 硬门（不可绕过）

> 在你说清楚打算做什么、并得到用户明确同意之前，**不要写任何实现代码、不要 scaffold 项目、不要调用任何实现类 skill**。
> 这个门适用于所有任务。任务简单到什么程度，流程就简化到什么程度；但"必须先获批"这件事从不简化。

## 三档分级

问第一个问题之前，先**大声说出**你判断这是哪一档，让用户有机会纠正：

### Spike（可行性探索）
- 长这样："能不能做 X？"、"试试 Y？"、"先不管糙不糙"
- 产出是一个**答案**，不是要保留的代码。
- 做法：2-3 句话说清问题和你打算怎么试，点头就去试，越便宜越好。结论写出来；试出来的代码标记为"一次性"。
- 不写设计文档，不写 spec。

### Bounded（有界改动）
- 长这样：在现有 repo 里改一个已有流程——加个 flag、加个小接口、改一个文件。
- **"bounded" 看的是 repo 里有没有现成流程可读，不是看你对这类项目熟不熟**。新 repo 里没有现成流程，就是 architectural。
- 做法：问关键的澄清问题，在对话里给一个简短设计（几句话到几段话），然后**停**。用户说"好"才动手。
- 不写 spec 文件，不写实现计划文档。

### Architectural（架构级）
- 长这样：新项目、新子系统、改组件之间的组合方式、改别人依赖的接口。
- 走完整流程：提问 → 方案 → 分段设计 → 写 spec → 写实现计划（见 `writing-plans`）。

**档位是单向棘轮**：任务进行中发现隐藏复杂度，就升级档位——停下来，说明情况，往上走。任何东西都不会降级。拿不准就走更重的那档。

## 红旗："太简单了不用获批"

| 心里的声音 | 真相 |
|---|---|
| "这太简单不用设计" | 简单 = 简短设计，不是没设计。对话里两句话，然后获批。 |
| "我标成 bounded 就能跳过 spec" | 找个标签想跳过流程，这个念头本身就是信号——走更重的档。 |
| "bounded 且设计明显，我边说边写" | 门是"获批"，不是"设计长度"。先说，停，等"好"。 |
| "我懂这种 app，所以 bounded" | bounded 看 repo 不看你。新项目没有现成流程 = architectural。 |
| "spike 能跑，代码就留着" | spike 的产出是答案。留代码是新需求，重新分级。 |
| "已经做了一半，不用重新分级" | 隐藏复杂度出现时停下升级，别硬撑。 |

## 流程

**Spike：**
1. 看一眼项目上下文，够框定问题就行
2. 抛出问题 + 探查方案（2-3 句）
3. 等点头
4. 最便宜地试
5. 报告结论；试出来的代码标记为一次性

**Bounded：**
1. 看项目上下文（文件、文档、最近 commit）
2. **一次只问一个**澄清问题，问最关键的
3. 在对话里给简短设计：做法、动哪些文件、怎么测
4. **停**，等用户明确说"好"
5. 获批后按正常 TDD 流程实现（见 `test-driven-development`）

**Architectural：**
1. 看项目上下文
2. 一次一个问题：目的、约束、成功标准
3. 提 2-3 个方案，带 trade-off 和你的推荐
4. 分段给设计，每段问"这部分对吗"
5. 写 spec 到 `docs/specs/YYYY-MM-DD-<topic>.md` 并 commit
6. spec 自审：占位符扫一遍、前后一致、范围是否过大、有没有歧义——发现就修
7. 让用户 review spec
8. 批准后，进入 `writing-plans` skill

## 设计的两个原则

- **拆小、单一职责**：每个单元能独立理解、独立测试。能回答"它做什么、怎么用、依赖谁"吗？
- **YAGNI**：每个方案都把没要求的功能砍掉。真需要时再加。

## 多步任务的一个提醒

如果用户一句话描述了多个独立子系统（"做个平台，带聊天、文件存储、计费、分析"），**立刻指出来**，不要花时间细化一个需要先拆解的项目。帮他拆成子项目，每个子项目走自己的 spec → plan → 实现循环。
