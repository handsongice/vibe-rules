# 写实现计划

## 核心假设

写计划时，假设执行者是个**有干劲但没品味、没判断力、不了解这个代码库、不爱写测试**的初级工程师。你要把所有他需要知道的东西写全：每个任务动哪些文件、代码长什么样、怎么测。

不要假设他会问、会查、会自己决定。

## 计划文件位置

存到项目里 `docs/plans/YYYY-MM-DD-<feature>.md`，commit。
文件开头放状态行（`> status: draft|active|done|abandoned · updated: YYYY-MM-DD`）：
开写时 `active`，按计划做完后改 `done`——`done` 的计划下一个 agent 不用重读。

## 头部必须有

```markdown
# <功能名> 实现计划

> status: active · updated: YYYY-MM-DD

**目标**：一句话说清做什么
**架构**：2-3 句说清做法
**技术栈**：关键技术/库
**Spec**：对应 docs/specs/xxx.md 路径

## 全局约束
（从 spec 抄过来：版本下限、依赖限制、命名规则、平台要求，一行一条，原值照抄）

---
```

## 任务切分

**一个任务 = 一个独立可测、值得一次 review 门的最小单元。**
- 把 setup、配置、scaffold、文档**折进**需要它的那个任务里，不要单独成任务。
- 只有当 reviewer 有理由"批 A 拒 B"时才拆成两个任务。
- 每个任务结束都要产出可独立测试的东西。

**每个步骤是一个动作（2-5 分钟）：**
- "写失败测试" —— 一步
- "跑一下确认它真的失败" —— 一步
- "写最小实现让它过" —— 一步
- "跑测试确认过了" —— 一步
- "commit" —— 一步

## 任务模板

```markdown
### Task N: <组件名>

**文件：**
- 新建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/test.py`

**接口：**
- 消费：本任务用到前面任务产出的什么（精确签名）
- 产出：后面任务要靠本任务的什么（精确函数名、参数、返回类型）

- [ ] **Step 1: 写失败测试**
（贴实际测试代码）

- [ ] **Step 2: 跑测试确认失败**
跑：`pytest ...`
预期：FAIL，原因是 XXX

- [ ] **Step 3: 写最小实现**
（贴实际代码）

- [ ] **Step 4: 跑测试确认通过**
跑：`pytest ...`
预期：PASS

- [ ] **Step 5: commit**
（贴 git 命令和 message）
```

## 禁止出现的占位符（计划失败）

- "TBD" / "TODO" / "稍后实现" / "补全细节"
- "加合适的错误处理" / "加校验" / "处理边界情况"
- "为 XX 写测试"（但不贴测试代码）
- "类似 Task N"——把代码重复一遍，因为执行者可能跳着看
- 只说做什么、不说怎么做的步骤
- 引用任何在别的任务里没定义的类型/函数/方法

## 自审（写完计划后自己过一遍）

1. **Spec 覆盖**：spec 里每条要求都能指到某个任务吗？漏了就补。
2. **占位符扫描**：搜上面那张表里的红旗词，发现就修。
3. **类型一致**：Task 3 叫 `clearLayers()`，Task 7 不能写成 `clearFullLayers()`。
4. **全局约束**：每个任务都隐含遵守了头部的全局约束吗？

发现问题直接改，不用再走一轮自审。

## 什么时候**不要**用这个 skill

- Bounded 任务（见 brainstorming）：对话里两句话设计 + 获批就够，不写计划文件。
- 20 行以内的改动：直接做。
- Spike：产出是答案，不是代码。
