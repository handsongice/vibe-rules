# 生产问题排查

> 通用的"找根因"方法论见同目录的 `systematic-debugging/SKILL.md`。本文件只讲生产环境特有的流程（止血、监控、不重启就挂着看）。

## 触发条件
问题发生在生产环境、影响真实用户、且不能随便重启/回滚的时候。

## 步骤（按顺序，不要跳）

1. **先止血，再定位**
   - 影响面多大？单个用户还是全站？什么时候开始的？
   - 最近有没有发版？有没有流量突增？
   - 如果正在持续恶化，先回滚最近一次发版（不是"先看看日志"）。

2. **收集证据，不要猜**
   - 拉最近 30 分钟的错误日志（按 trace id / request id 过滤）。
   - 看监控：CPU、内存、QPS、延迟、错误率、DB 连接池。
   - 问用户：怎么操作的？什么浏览器/客户端版本？有没有截图？
   - **禁止**：在没看到日志之前就说"我觉得是 X 问题"。

3. **形成一个假设，验证它**
   - 写下来："我认为是 Y，因为 Z 现象"。
   - 找一个能证实或证伪这个假设的证据。
   - 一个假设一个假设地验证，不要同时试五种修复。

4. **修复前想清楚**
   - 修复方案的影响面是什么？要不要停服？要不要改数据？
   - 改生产数据前，先备份/导出当前状态。
   - 要不要写一个复现测试？（见 `global/testing.md`）

5. **事后**
   - 在 `global/anti-patterns.md` 追加一条记录。
   - 如果是 agent 之前的决策导致的，写清楚怎么避免下次。

## 验收标准
- [ ] 有明确的根因，不是"重启就好了"。
- [ ] 有防止复发的动作（测试 / 监控 / 代码改动 / 文档）。
- [ ] 记录进 anti-patterns。

## 绝对不要做
- 不要直接 `rm -rf` 生产目录。
- 不要在生产数据库上跑 `DROP` / `TRUNCATE` / 不带 `WHERE` 的 `UPDATE`/`DELETE`。
- 不要为了"快速修复"跳过日志直接改代码上线。
