# Code Review（自审）

## 触发条件
功能代码写完、测试跑通之后，交付给用户之前，主动走一遍。

## 步骤
按顺序问自己：

1. **正确性**
   - 边界条件：空输入、null、超长、并发、超时、部分失败？
   - 错误路径：异常会不会被吞？事务会不会不回滚？资源会不会泄漏？
   - 假设：我有没有在心里假设"输入一定是 X"？代码里有没有体现？

2. **可读性**
   - 命名：变量名读起来像人话吗？函数名是动词吗？
   - 一个函数超过 50 行？一个文件超过 300 行？
   - 有没有重复逻辑可以抽（但不要为了 DRY 抽得过度）？

3. **安全**（见 `global/security.md`）
   - SQL/命令参数化？输入校验？错误信息泄露？

4. **与现有代码一致性**
   - 这个项目里同类功能是怎么写的？我写的和它风格一致吗？
   - 有没有现成的 util / helper 我重复造了？

5. **测试**
   - 新逻辑有测试吗？边界条件有覆盖吗？
   - 我改的老代码，相关测试还过吗？

## 输出格式
不要笼统说"没问题"。按下面格式：

```
自审结果：
- [必须改] <问题>：<位置>，<建议改法>
- [建议改] <问题>：...
- [可接受] <权衡点>：...
```

## 验收标准
- 每个"必须改"都已处理或明确向用户说明为什么不改。
- 不允许出现"代码没问题"这种结论——只要你认真看，总能找出至少一个改进点。
