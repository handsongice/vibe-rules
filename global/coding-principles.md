# Coding 行为四原则（Karpathy 风格）

> 来源：Andrej Karpathy 关于 LLM 编码常见问题的观察，由 multica-ai/andrej-karpathy-skills 整理。
> 本文件是 `iron-rules.md` 的行为层补充。铁律是"不许做"，这里讲"怎么做才对"。
>
> **适用边界**：这四条偏向"谨慎优先"。改一个 typo、改一行明显的 bug，不用全套流程；非平凡任务必须走。

---

## 原则 1：动手前先想清楚

**不要默默假设、不要藏起困惑、不要假装没有歧义。**

- 有假设就说出来："我假设 X，对吗？"
- 有多种理解就列出来："这事儿可以是 A 也可以是 B，你要哪个？"
- 发现有更简单的做法就直说，不要为了显得技术高深搞复杂。
- 看不懂就停下来：说清楚哪里看不懂，问。不要硬着头皮写。

**反例（"导出用户数据"）：**
agent 没问就写了个导出全部用户到 JSON/CSV 的函数。问题：导全部还是筛选？落盘还是下载？哪些字段？用户量多大？隐私怎么处理？

**正确做法**：动手前先列 3-4 个关键假设让用户确认。

## 原则 2：简单优先

**用最少的代码解决问题。不写任何"以后可能用到"的东西。**

- 不加用户没要求的功能。
- 单次使用的代码不要抽抽象类/策略模式。
- 不做没要求的"灵活性"和"可配置性"。
- 不为不可能发生的场景写错误处理。
- 写完回头看：200 行能压成 50 行就重写。
- **自检**："一个资深工程师看到这段会觉得过度设计吗？"会就改。

**反例（"写个算折扣的函数"）：**
agent 上来就 `DiscountStrategy` 抽象基类 + `PercentageDiscount` + `FixedDiscount` + `DiscountConfig` dataclass + `DiscountCalculator`——一个 5 行的函数被写成 50 行类层级。

**正确做法**：
```python
def calculate_discount(amount: float, percent: float) -> float:
    return amount * (percent / 100)
```
真要多种折扣类型的时候再重构，那时候你已经知道真实需求了。

### 动手前过一遍这个决策梯子（Ponytail 风格）

写任何代码前，从第一步开始问，第一个成立的就是答案：

1. **这东西真需要存在吗？** 不需要就别写（YAGNI）。
2. **代码库里已经有了吗？** 有就复用，不要重写。
3. **标准库能做吗？** 能就用标准库。
4. **原生平台功能能做吗？** 比如日期选择用 `<input type="date">`，不要装 flatpickr；浏览器/操作系统/框架自带的能力先用完。
5. **已经装的依赖能做吗？** 能就别加新包。
6. **一行能搞定吗？** 能就一行。
7. **最后才写：** 最小可用实现。

**梯子的前提**：先读懂问题、追完真实数据流，再开始爬梯子。懒在解决方案上，不懒在读代码上。一个你没读懂的小 diff，只是"把懒包装成效率"。

**这些东西不省**：
- 理解问题（读全、追流）
- 信任边界的输入校验
- 防数据丢失的错误处理
- 安全、无障碍
- 用户明确要求的东西

**Bug 修复 = 修根因，不是补症状**：grep 你要改的函数的所有调用方，在共享函数里修一次——一个 guard 比 N 个调用方各补一个 guard 更小。只修 ticket 里提到的那条路径，旁边那个调用方还是坏的。

**刻意简化要标记**：如果为了快而做了简化（全局锁、O(n²) 扫描、朴素启发式），在代码里加一行注释说明天花板和以后怎么升级，比如：`# SIMPLIFICATION: 这里用 O(n²)，数据量 < 1k 时够；超过了换 B-tree`。不要假装它是完美方案。

## 原则 3：外科手术式改动

**只动必须动的行。清理自己留下的垃圾，不清理别人的。**

改老代码时：
- 不要"顺手优化"旁边的代码、注释、格式。
- 不要重构没坏的东西。
- 哪怕现有风格你不喜欢，也**保持现有风格**。
- 发现不相关的死代码：**指出来，不要删**。

你的改动产生了孤儿（import、变量、函数没人用了）：
- 删掉你这次改动导致的孤儿。
- 不要删早就存在的死代码，除非用户要求。

**自检**：每一行 diff 都能追溯到用户这次的需求吗？不能就撤。

**反例（"修复空邮箱导致崩溃的 bug"）：**
agent 顺手把邮箱校验加强了、加了用户名长度/字符校验、重写了注释、加了 docstring、改了引号风格。

**正确做法**：只改让空邮箱不崩的那几行。其他问题在交付时提一句"我注意到用户名校验也很弱，要不要单独处理？"——让用户决定。

## 原则 4：目标驱动执行

**把命令式任务翻译成可验证的目标，然后循环到通过为止。**

| 用户说 | 你应该翻译成 |
|---|---|
| "加个校验" | "为非法输入写测试，然后让测试通过" |
| "修这个 bug" | "先写一个复现这个 bug 的失败测试，再修到通过" |
| "重构 X" | "改之前测试全绿，改之后测试也全绿" |
| "优化性能" | "基准从 500ms 到 <100ms，写 micro-benchmark 验证" |

多步任务时，先写一个带验证的计划：
```
1. 做 X  → 验证：跑 Y，看到 Z
2. 做 W  → 验证：...
3. 做 V  → 验证：...
```

强的成功标准让 agent 能自己循环下去；弱的标准（"搞好它"）只会让你来回问。

**反例（"修复认证系统"）：**
agent 说"我来看看代码、找问题、改进、测试"——没有成功标准，改完说"应该好了"。

**正确做法**：先问清楚具体是什么问题（"改密码后旧 session 没失效？"），然后：
1. 写测试：改密码 → 旧 session 必须失效 → 现在是红的
2. 实现：改密码时清 session → 测试变绿
3. 边界：多端登录、并发改密 → 补测试
4. 回归：全量 auth 测试仍绿

## 什么时候这四条在起作用

看到下面这些现象说明在起作用：
- diff 里只有用户要求的改动，没有 drive-by refactor
- 代码第一次写出来就不复杂，不需要"简化第二轮"
- agent 先问清楚再动手，而不是写错了再道歉
- PR 小、干净、好 review

## 代码体型与组织（硬数字）

下面这些是经验值，不是教条。新项目遵守，老项目不强求。

- **函数 < 50 行**。超过就拆。
- **文件 200-400 行典型，800 行上限**。超过 800 行说明职责太杂，考虑拆。
- **嵌套 < 4 层**。if/for/while 套到第 4 层就该抽函数或早返回。
- **按 feature/domain 组织代码，不按 type**。不要 `controllers/ services/ models/` 三个大目录装所有东西；按业务域切，比如 `order/` 下面自己有 controller/service/repository。
- **一个文件一个职责**。高内聚低耦合。
- **API 响应统一信封**：`{ success: bool, data, error: { code, message }, pagination? }`。不要有的接口返回数组、有的返回 `{result: ...}`。

这些数字不是为了好看，是为了让 agent 改代码时一眼知道"这个文件是不是太大了、该拆了"，也是为了 code review 时快速定位问题。

## 一句话总结

> 好代码是**今天的问题用最简单的方式解决**，而不是**明天可能的问题提前设计**。
