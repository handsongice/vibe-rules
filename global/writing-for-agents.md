# 写给 agent 看的文档（元规范）

> 这个文件管的是：**你往本库里加新文件、改 AGENTS.md、写 skill 时，怎么写 agent 才读得动。**
> 来源：mattpocock/skills 的 writing-for-agents，按我们的库重写。

## 为什么要有这个文件

agent 每次运行都走同一种处理流程，不是每次产生同样的输出。你写的文档是在这个流程上**安装一个可预测的杠杆**。写得不对，agent 就不触发、过早结束、或者完全无视。

## 两个预算

你往库里加的每一行，花的是这两个预算之一：

- **上下文预算**：每轮都占 token 的东西——AGENTS.md 里的一行、skill 的 description。没触发也在烧。
- **认知预算**：人（也就是你）要记住"有这个文档、什么时候翻"。

新增文件时问自己：这行字是每轮都要让 agent 看到，还是特定场景才该翻？前者要短，后者要在索引里写清楚触发条件。

## 信息层级（重要）

一份文档分三层：

1. **文件内步骤**：agent 按顺序做的动作。最核心。
2. **文件内参考**：按需查的规则、定义、清单。
3. **外置参考**：推到另一个文件，通过索引里的"指针"触发才加载。

**渐进披露**就是把不是每个分支都用的东西推到第 3 层。判断标准：**这个文档的所有分支都需要它吗？** 都需要就放文件里；只有部分分支用就推出去。

反例：一个 skill 里 800 行，其中 200 行只在"用户说西班牙语"这个分支才用——那 200 行应该拆出去。

## 指针（context pointer）怎么写

索引里"见 `global/xxx.md`"这一行就是指针。**指针的措辞**决定 agent 什么时候真的去读那个文件，比目标文件本身还重要。

写指针时：
- **开头就放触发词**。"修 bug 前先读 systematic-debugging"比"这里有个调试 skill"触发率高得多。
- **一个分支一个触发**。"修 bug / 测试挂了 / 行为不对"——这三个是同一分支的同义词，合并成一句。
- **不重复正文里已经有的身份**。指针只说"什么时候读"，不说"里面有什么"。

## 步骤要有"完成标准"

每个步骤结束时，agent 必须能判断"做完了吗？"：

- ✅ 好："跑 `pytest -x`，全绿"——可验证、穷尽。
- ❌ 坏："理解一下代码"——agent 会假装理解了就走。

模糊的完成标准会导致**过早完成**：agent 看到后面还有步骤，就急着把当前步骤糊弄过去。
修法：先把标准写具体；实在写不具体，才考虑把后续步骤拆到另一个文件里。

## 正面表述，不要写否定句

> "不要想大象"——大象立刻就在你脑子里了。

否定句会把被禁止的行为**激活**，而不是压制它。写正面目标：

- ❌ "不要随便重构" → ✅ "每个改动的行都能追溯到用户这次的需求"
- ❌ "不要用 any" → ✅ "用 unknown 加类型守卫"
- ❌ "不要忘记跑测试" → ✅ "改完跑 `pytest -x`，把结果贴出来"

只有当没法用正面说时才用否定句，而且必须配正面目标。

## 用模型已有的概念词

选一个模型预训练里已经有的概念词（red/green loop、tight、YAGNI、外科手术式），反复用它，agent 就会把一整串行为挂到这个词上。不要自己造词——造词要花 token 解释，预训练词免费。

## 删减纪律

- **单一真相源**：一个规则只写一处。其他地方引用，不要复制。
- **环境即真相**：`package.json` scripts、目录结构、`--help` 能查到的，不要在文档里抄一遍。文档只写"查不到的、背后的原因、坑"。
- **删 no-op 句**：agent 默认就会做的事，写出来是浪费。测试方法："这句话不写，agent 行为会变吗？" 不变就删整句。
- 警惕**沉积物**：因为"加着安全、删着怕"，文档越堆越厚。每季度来一轮 pruning。

## 给这个库加新文件时的检查清单

- [ ] 文件名和触发条件写清楚了吗？
- [ ] 开头 3 行能不能让 agent 判断"这是不是我现在该读的"？
- [ ] 步骤有可验证的完成标准吗？
- [ ] 有没有把"环境能查到的"又抄了一遍？
- [ ] 有没有否定句可以改成正面？
- [ ] 和已有文件重复的内容删了吗（改成引用）？
